# AGENTS.md

This file applies to the entire repository.

## Mission

Build **CISSP Quiz Trainer**, a local-first Windows 11 desktop application primarily for the owner's personal CISSP study and exam preparation. Prioritize reliable daily practice and review with a simple interface.

The product and architecture baseline is documented in `docs/requirements-v0.3.md`. Treat that document as the primary source of truth unless the user explicitly changes the requirements.

## Technical baseline

- Go toolchain: **1.27.x** for development, CI, and release builds. The `go 1.23.0` directive in `go.mod` is the module's declared minimum Go version and language semantics baseline, not the selected build toolchain. It does not by itself establish full dependency compatibility with Go 1.23.0.
- Desktop shell: **Wails v2**, with the current dependency and CLI at **v2.15.0**. Stay on the stable v2 line unless an explicit migration is requested.
- Frontend: **Vue 3 + TypeScript + Vite**.
- State management: **Pinia**.
- Database: **SQLite**.
- Database access: Go `database/sql` behind repository interfaces.
- Package manager: **npm**.
- Target platform: **Windows 11 x64 first**.
- Distribution: GitHub Releases containing a Windows executable/archive.

## Architecture boundaries

Keep dependencies flowing in this direction:

```text
Vue UI
  ↓
Wails binding / thin application adapter
  ↓
Service / use-case layer
  ↓
Repository interfaces
  ↓
SQLite repository implementations
```

Rules:

1. Vue components must not access SQLite or filesystem persistence directly.
2. Wails binding methods should be thin. Put business rules in `internal/service`.
3. Service code must depend on repository interfaces, not concrete SQLite implementations.
4. SQL belongs under `internal/repository/sqlite` or `internal/database`, not in Vue or service code.
5. Import parsers belong under `internal/importer` and should convert external files into validated domain data before persistence.
6. Multi-table writes that must succeed or fail together must use transactions.
7. Enable SQLite foreign-key enforcement for application connections.
8. Database schema changes require an explicit migration.
9. Keep the application local-first. Do not add telemetry, accounts, cloud sync, remote analytics, or network calls unless explicitly requested.

## Question-file contract

The machine-readable import format is the JSON Question Schema v1 defined in `docs/requirements-v0.3.md`.

Do not silently make incompatible schema changes. Import code must validate `schemaVersion`, reject malformed required fields with actionable errors, detect duplicates/conflicts, never silently discard invalid questions, and preserve stable question IDs.

If a schema-breaking change is required, update documentation and introduce a new schema version.

## CISSP behavior rules

- Study mode may reveal answers after the learner submits the current question.
- Exam mode must not reveal correct answers before the session is completed.
- Record answer history independently from question content.
- Keep wrong-question history even after a question later becomes mastered.
- Domain IDs remain 1-8 as defined in the requirements.
- FIRST / BEST / MOST / NEXT and related question types are first-class metadata.

## Development commands

Prerequisites:

- Go 1.27.x toolchain
- Node.js 22.x as the development and CI baseline; other maintained releases require compatibility validation with this project
- npm (no project-specific version is currently pinned)
- Wails CLI v2.15.0, matching the current dependency in `go.mod` and the CI installation command
- WebView2 for local Windows desktop runs

See [README version declarations](README.md#version-declarations) for the distinction between configured versions and verified compatibility. Do not treat an installed alternative Node.js version as validated until the required project checks pass.

Fresh checkout:

```bash
go mod download
cd frontend
npm install
npm run build
cd ..
go vet ./...
go test ./...
```

Run the app:

```bash
wails dev
```

Production smoke build:

```bash
wails build -clean
```

The frontend must be built before commands that compile the root Wails package on a completely fresh checkout because `main.go` embeds `frontend/dist`.

## Required checks

For normal feature changes, run:

```bash
cd frontend
npm run type-check
npm run build
cd ..
gofmt -w .
go vet ./...
go test ./...
wails build -clean
```

Do not claim a check passed if it was not run. If the environment cannot run a Windows/Wails build, state that clearly and run every portable check available.

## Go conventions

- Prefer explicit interfaces at architectural boundaries.
- Wrap errors with context using `fmt.Errorf("...: %w", err)`.
- Do not use `panic` for ordinary application errors.
- Pass `context.Context` through I/O operations where appropriate.
- Prefer table-driven tests for validation, scoring, import, and statistics logic.
- Keep domain logic independent of Wails where practical.
- Use UTC for persisted timestamps unless a requirement explicitly needs otherwise.
- Avoid global mutable state.

## Frontend conventions

- Use TypeScript for application modules.
- Keep Wails/API calls behind frontend service modules.
- Use Pinia for cross-page state and local component state for presentation-only concerns.
- Prefer accessible semantic HTML and keyboard-friendly controls.
- Do not put scoring, import validation, or persistence rules in Vue components.
- Keep answer-revealing state explicit so exam mode cannot accidentally expose solutions.

## Tests

Prioritize tests for:

- JSON schema validation
- duplicate/conflict detection
- quiz scoring
- session completion
- wrong-question progress
- statistics
- SQLite repository CRUD and transactions
- migrations
- backup/restore validation

Bug fixes in core logic should add regression tests when practical.

## Data safety

- Do not delete or rewrite user data implicitly during startup.
- Backups and restores must validate versions before modifying the active database.
- Prefer atomic/transactional changes.
- Never commit real user databases or private question sets.

## Scope control

For v0.1, follow the personal-use boundary in sections 1.1 and 35 of `docs/requirements-v0.3.md`. Other feature descriptions and future-version lists do not automatically expand the MVP or the current task.

### Keep the project simple

- Optimize for one learner using a local installation. Possible future use by a few people means independent installations with separate local data by default. Sharing question files does not imply shared accounts, shared databases, synchronization, or collaboration features.
- Prioritize the daily loop: import a JSON question set, practice, read explanations, revisit wrong/favorite questions, view basic results, and back up or restore learning records.
- Defer Markdown/paste parsing, in-app question editing and merging, advanced quiz generation, rich dashboards, automated learning diagnosis, and spaced-repetition models until a concrete user need selects them. A roadmap entry alone is not authorization to implement it.
- Use a small number of clear screens. Related views may share a page; do not build a separate page for every heading in the requirements. Prefer readable text, simple lists, and basic filters over decorative animation or elaborate charts.
- Keep the existing Wails / service / repository / SQLite boundaries. Implement concrete use cases with small services and explicit repository interfaces; do not add generic CRUD frameworks, generic repositories, plugin systems, event buses, dependency-injection frameworks, extra processes, or alternate storage backends for hypothetical future reuse.
- Prefer straightforward queries and synchronous operations where they meet the actual need. Introduce caches, background workers, and performance infrastructure only for a demonstrated requirement or measured problem. Keep long-running file operations responsive without building a general job platform.
- Do not build a full question-versioning or audit framework merely to enable optional editing. Deferring editing is acceptable; any later edit/delete feature must preserve existing answer history.
- Keep import validation, stable question identity, correct scoring, idempotent submission, transactions, migrations, and safe backup/restore. Simplicity must not cause silent data loss, duplicate answer counts, or answer disclosure during an exam session.
- Validate the actual workflow and failure paths with focused tests. Avoid broad test matrices and new testing infrastructure solely for hypothetical future scale; continue to run the required checks for feature changes.
- Before adding a dependency, abstraction, setting, or feature, identify the current user problem and why existing code cannot handle it simply. If the only justification is possible future use, defer it. Make routine implementation choices autonomously; ask the user only when a material scope decision remains unclear.

Do not add authentication, cloud sync, AI APIs, online question banks, payments, ads, or unrelated framework migrations unless explicitly requested.

If a task changes architecture, schema, or product scope, update the relevant documentation in the same change.
